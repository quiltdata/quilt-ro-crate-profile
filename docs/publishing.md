# How an RO-Crate profile gets published

What publishing this profile requires, written after reading the live configuration of
working profiles rather than only the guidance about them.

## It takes two repositories

| Layer | Job | Repository |
|---|---|---|
| Hosting | Serves the HTML specification, the Profile Crate, the examples | This one, via GitHub Pages |
| Permalink | Maps the permanent URI onto the hosting, with content negotiation | [`perma-id/w3id.org`](https://github.com/perma-id/w3id.org), by pull request |

Both are needed. Hosting alone cannot satisfy the specification's requirement that the
profile URI resolve to different representations. The permalink layer has nothing to point
at without the hosting.

## Content negotiation has to live at w3id

The [profiles specification](https://www.researchobject.org/ro-crate/specification/1.2/profiles.html)
requires the profile URI to resolve to a human-readable description, and allows it to also
resolve to a Profile Crate. That is content negotiation, and **GitHub Pages cannot do it** —
Pages only maps file extensions to content types.

So negotiation belongs in the w3id `.htaccess`. Confirmed against
[Process Run Crate](https://w3id.org/ro/wfrun/process/0.6):

```
w3id.org/ro/wfrun/process/0.6
  Accept: text/html           -> .../process_run_crate/                text/html
  Accept: application/ld+json -> .../ro-crate-metadata.jsonld          application/ld+json
  Accept: */*                 -> .../process_run_crate/                text/html
```

Both destinations are plain static GitHub Pages. The negotiation happened at the w3id Apache
layer. The rules doing it are in `ids/ro/wfrun/process/.htaccess` in the w3id repository, and
they are the model for [`../w3id/.htaccess`](../w3id/.htaccess): an `AddType` block, one
`RewriteCond`/`RewriteRule` pair per media type, then an unconditional HTML rule last as the
default. Redirects are `303`.

## The `.json` / `.jsonld` trap

RO-Crate requires the metadata document to be named `ro-crate-metadata.json`. GitHub Pages
serves that with the wrong content type. Measured:

| File | Content-Type served |
|---|---|
| `ro-crate-metadata.json` | `application/json; charset=utf-8` |
| `ro-crate-metadata.jsonld` | `application/ld+json` |

So publish **both**: the `.json` because the specification requires that filename, and a
`.jsonld` copy as the target a client asking for `application/ld+json` can be redirected to.
This is the aliasing the
[RO-Crate JSON-LD appendix](https://www.researchobject.org/ro-crate/specification/1.3/appendix/jsonld.html)
recommends for CDNs. It suggests a symlink; a generated copy is safer because GitHub Pages
does not reliably follow symlinks. Either way it must be generated by
[`../build.sh`](../build.sh) rather than maintained by hand, or it goes stale silently.

## Do not use the `ro/terms/` namespace for a profile

A tempting shortcut is to register under `https://w3id.org/ro/terms/<name>`, the RO-Crate
public namespace, since the redirect infrastructure already exists. That does not work for a
profile.

The catch-all rules in `ids/ro/terms/.htaccess` are:

```apache
RewriteCond %{HTTP_ACCEPT} application/ld\+json
RewriteRule (.+)$ https://www.researchobject.org/ro-terms/$1/context.jsonld [R=303,L]
RewriteCond %{HTTP_ACCEPT} text/turtle [OR]
RewriteCond %{HTTP_ACCEPT} \*/turtle
RewriteRule (.+)$ https://www.researchobject.org/ro-terms/$1/vocabulary.ttl [R=303,L]
RewriteRule ^(.*)$ https://www.researchobject.org/ro-terms/$1/vocabulary.csv [R=303,L]
```

So such a URI can only ever resolve to a vocabulary CSV, a Turtle file, or a JSON-LD context,
all hosted on `researchobject.org` rather than by the profile's authors. None of those is a
human-readable profile description, so the URI cannot satisfy the requirement.

`ro/terms/` is for **ad-hoc terms**, and the specification is explicit that it exists for
authors who do not have the resources to create and maintain an HTML page. A project that can
host its own page should claim its own namespace, which is what every mature profile does:
`w3id.org/cpm/ro-crate`, `w3id.org/workflowhub/workflow-ro-crate`,
`w3id.org/ro/wfrun/process/0.6`.

## The w3id pull request

Current process, from the `perma-id/w3id.org` README. Namespaces live under `ids/`; older
guidance describing top-level directories is out of date.

1. Fork `perma-id/w3id.org`.
2. Create `ids/<namespace>/` containing `.htaccess` (redirect rules) and `README.md`
   (identifier and contact info for humans).
3. Open a pull request.

The maintainers ask for contact details in the README or an `.htaccess` comment, changes
tested against a local checkout, multiple commits squashed, and a commit message that names
the project rather than the default "Create `.htaccess`". Emailing
`public-perma-id@w3.org` is an alternative, but the pull request is preferred.

There is no formal naming policy. Current practice is to claim a top-level directory and add
project-specific second-level identifiers, `w3id.org/PROJECT-ID/SUB-ID`. Administrators may
refuse names that are too generic or that might be needed for future service expansion, so a
scoped request such as `quilt/ro-crate` is safer than a bare product name.

## Versioning

Two decisions, and they should deliberately not match.

- **The profile URI SHOULD be versioned** MAJOR.MINOR. So `https://w3id.org/quilt/ro-crate/0.1`,
  with the unversioned `https://w3id.org/quilt/ro-crate` resolving to the latest. This mirrors
  `ids/ro/wfrun/process/.htaccess`, which has a `^$` rule for latest and a `^(.+)$` rule for a
  specific version.
- **Term IRIs should NOT be versioned.** The Common Provenance Model profile keeps its terms at
  `w3id.org/cpm/ro-crate#CPMProvenanceFile`, unversioned, while the profile versions. Terms
  outlive profile revisions, and the specification warns that updates should not remove or
  re-point published terms. Versioning them would break every existing crate on each release.

A fragment is never sent to the server, so a term IRI is the same HTTP request as the bare
profile URI. It resolves to the profile page, and that page needs matching anchor `id`s for a
browser to land on the definition. [`../build.sh`](../build.sh) emits them; without them the
term IRIs resolve but land nowhere useful.


   its check runs `upload_profiles.py --dry-run`, which fetches the URI with

Elapsed time for step 4: the pull request was opened and merged the same day.

### A note on `.nojekyll`

This repository disables Jekyll, so Pages serves every file verbatim rather than letting
Jekyll decide what to publish. The tradeoff is that Pages no longer renders `README.md` as a
directory index, so the site root would 404; [`../build.sh`](../build.sh) generates a root
`index.html` listing the published versions instead.
